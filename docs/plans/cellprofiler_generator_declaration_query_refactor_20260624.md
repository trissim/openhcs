# CellProfiler Generator Nominal Policy Planning Refactor

## Purpose

Refactor the CellProfiler pipeline generator so it emits OpenHCS pipeline code
from selected existing nominal module policies instead of owning module-specific
semantics.

The generator should remain the code-emission and orchestration layer. It should
not be the place where OpenHCS learns that `TrackObjects` runs over timepoint,
`GrayToColor` preserves channel identity, `SaveImages` keeps otherwise-dead
image artifacts alive, or `CorrectIlluminationCalculate` changes grouping based
on one CellProfiler setting.

The simple architectural rule is:

```text
CellProfiler module class declarations own module-specific rules and quirks.
Catalogs are generated views of those declarations.
OpenHCS generator, compiler, runtime, and adapter code stay generic.
```

A compiler or validator should be able to check whether a generated
`FunctionStep` is properly configured for a CellProfiler module by resolving that
module's class declaration and asking its ABC contract. It should not need a
concrete `if module_name == ...` branch for `SaveImages`, `TrackObjects`,
`MaskImage`, `Watershed`, or any other module. If a module needs special
behavior, the special behavior belongs on the registered module class or an
inherited nominal policy hook.

Do not introduce a declaration facade, strategy, builder, or service that only
wraps existing registries. The class that represents the module is the single
source of truth. It can inherit existing policy parents, select existing binding
or function-resolution executors, and expose validation hooks, but adapter,
generator, compiler, and runtime code must derive from that typed owner instead
of copying module facts into local tables.

The absorbed CellProfiler module catalog must be autogenerated from
AutoRegisterMeta-backed class declarations. `contracts.json`,
`validated_contracts()`, and compatibility catalog exports may exist only as
generated/read-model projections; they must not be the hand-authored authority
for module names, function binding, generated `FunctionStep` semantics, or
module-specific rules.

## Current Shape

The current architecture is already partly nominal-policy-driven:

- `openhcs/interop/cellprofiler/module_semantics.py` declares manual module
  category, dimensionality, infrastructure status, and mask support. It is not
  yet the full module catalog authority.
- `openhcs/processing/backends/cellprofiler/library.py` currently loads
  `contracts.json` into `AbsorbedFunctionMetadata` and exposes
  `validated_contracts()`. That JSON-loaded map is a legacy compatibility path
  and must be replaced by a catalog derived from registered `CellProfilerModule`
  classes.
- `openhcs/interop/cellprofiler/symbol_table.py` declares and infers
  `ModuleArtifactContracts` through `ModuleContractBuilder` and
  `InferredModuleContractPattern`.
- `openhcs/interop/cellprofiler/module_settings_binding.py` owns
  `_ModuleSettingsBindingStrategy` for translating `.cppipe` settings to
  backend kwargs and invocation options.
- `openhcs/interop/cellprofiler/module_function_resolution.py` owns
  `_ModuleFunctionResolutionStrategy` for selecting backend functions.
- `openhcs/interop/cellprofiler/module_runtime_semantics.py` owns revision-
  specific runtime kwargs such as Watershed runtime-family selection.
- `openhcs/core/pipeline_image_schema.py` owns source schema semantics lowered
  from CellProfiler setup modules.

Earlier audit snapshots found `openhcs/interop/cellprofiler/pipeline_generator.py`
owning semantic exceptions that should be selected policy facts:

- `TrackObjectsProcessingComponentStrategy` hardcodes timepoint execution.
- `StraightenWormsProcessingComponentStrategy` hardcodes channel source-identity
  preservation under multi-image bindings.
- `GrayToColorProcessingComponentStrategy` hardcodes channel source-identity
  stacking for composite color outputs.
- `MeasureImageAreaOccupiedProcessingComponentStrategy` changes pairwise
  object-domain scoping.
- `CorrectIlluminationCalculateProcessingComponentStrategy` inspects
  `calculation_scope` and changes variable/group-by axes.
- `_save_images_required_artifacts(...)` hardcodes infrastructure artifact
  retention for skipped `SaveImages` modules.
- `PipelineGeneratorCodeEmitter.generate_steps_from_registry(...)` directly
  coordinates settings binding, function resolution, artifact contracts,
  execution-scope strategy, invocation options, materialization pruning, and
  generated source emission.

That was better than a raw `if module.name == ...` script because most behavior
was behind registered strategy families, but it still made the generator a
semantic hub. The target remains a planning architecture where those strategy
families own their module behavior and the generator consumes already-lowered
facts. The live-code recheck below supersedes the older generator-specific rows.

## Live Code Recheck, 2026-06-26

The live code is ahead of several older rows in this document. As of this
recheck, `pipeline_generator.py` no longer appears to host the named
`TrackObjectsProcessingComponentStrategy`, `StraightenWormsProcessingComponentStrategy`,
`GrayToColorProcessingComponentStrategy`, `MeasureImageAreaOccupiedProcessingComponentStrategy`,
or `CorrectIlluminationCalculateProcessingComponentStrategy` leaves described
above.

Current generator routing:

- `PipelineGeneratorRegistryStage.load_registry()` loads validated
  `CellProfilerModule` classes from the AutoRegisterMeta registry when no
  explicit legacy library root is provided.
- `PipelineGeneratorRegistryStage.bind_settings(...)`,
  `resolve_function(...)`, and `processing_components(...)` all require the
  selected `CellProfilerModule` class and call that class directly.
- `PipelineGeneratorCodeEmitter.generate_steps_from_registry(...)` still
  coordinates settings binding, function resolution, artifact lineage, and
  source emission inline, but those module-specific questions are now reached
  through the module class instead of generator-local processing leaves.

Remaining generator-side boundaries after this cleanup:

- `CellProfilerSymbolTable.compile(...)`, `ModuleArtifactContracts`, and
  `module_contract_literal(...)` remain the artifact-flow carrier consumed by
  the generator. Live `symbol_table.py` may already delegate more artifact
  contract work to declarations, but generator code still depends on that
  compiler result shape.
- Skipped infrastructure retained artifacts are still obtained through
  `cellprofiler_infrastructure_retained_artifacts(...)`. This is not a
  generator-local `SaveImages` helper anymore, but retained-artifact ownership
  still needs to stay on the infrastructure/module declaration side.
- `module_processing_components.py` now owns generic source-axis lowering,
  runtime-artifact lineage, and default processing-scope algebra. Its remaining
  declaration-adjacent surface is the absorbed-category-to-axis mapping for
  `image_operation`, `z_projection`, and `channel_operation`; those category
  labels are module-declaration facts and should not grow into a second module
  registry.
- Generated step emission still renders `source_bindings=` from the compiled
  artifact contract when the contract has direct source bindings. Any future
  plate-level source-binding handler work should keep this as a declaration or
  compiler-result concern, not a parallel MCP/UI rule.

## Forked Generator Algebra Audit, 2026-06-25

A parallel read-only audit confirmed the useful algebra:

```text
ModuleBlock
+ selected existing module policies
+ compiled artifact contract
-> CellProfiler module generation plan
-> FunctionStep source plus runtime ModuleArtifactContract
```

The generator/compiler should orchestrate that fold. They should not own module
facts. The existing surfaces that should pay rent as the query boundary are:

- `ModuleArtifactContracts`, `ModuleContractBuilder`, and
  `InferredModuleContractPattern` in `symbol_table.py`.
- `ArtifactSettingRole`, `ArtifactSettingClassifier`,
  `artifact_setting_symbols`, and `function_special_outputs` in
  `artifact_semantics.py`.
- `_ModuleSettingsBindingStrategy.bind(...)` in
  `module_settings_binding.py`, which already returns kwargs, invocation
  options, runtime semantics, and setting coverage.
- `_ModuleFunctionResolutionStrategy` in
  `module_function_resolution.py`.
- `ModuleRuntimeSemanticsBinding` in `module_runtime_semantics.py`.
- the future `CellProfilerModule` ABC root that every CellProfiler module class
  inherits from, with generic lowering machinery in
  `module_processing_components.py`.
- Runtime policy ABCs such as `CellProfilerPrimaryImageInputPolicy`,
  `CellProfilerSpecialInputPolicy`, `CellProfilerObjectInputPolicy`,
  `CellProfilerMeasurementRecordBuilder`, and
  `RelationshipEndpointResolver`.

The audit identified the duplicated semantic owners to remove at that time:

- `pipeline_generator.py` hosted module-specific processing leaves for
  `TrackObjects`, `StraightenWorms`, `GrayToColor`,
  `MeasureImageAreaOccupiedBinary`, and `CorrectIlluminationCalculate`. The ABC
  was useful, but the generator file was hosting module declarations. The
  2026-06-26 live recheck indicates those named leaves have since moved out of
  the generator.
- `_save_images_required_artifacts(...)` and its build-stage consumer hardcode
  `SaveImages` artifact retention. This belongs on the existing infrastructure
  policy family.
- `MODULE_FUNCTION_RESOLUTION_RULES` is a second registry-shaped table beside
  `_ModuleFunctionResolutionStrategy`; convert those entries into strategy
  leaves or inherited declarations inside that existing family.
- `RelateObjects` endpoint facts are still fragmented across contract building,
  endpoint resolution, row projection, and output recording. The endpoint
  policy should become the relationship endpoint SSOT that all of those callers
  query.
- `CorrectIlluminationApply` provenance lookup is still partly in generic
  output-request helpers. The `CorrectIlluminationApply` output context/value
  policies should own the `Orig*` source-output relationship.

Mechanical work is appropriate for constant/alias normalization and generated
leaf conversion inside existing ABC families. Hand design is still needed for
the generation-plan carrier, processing-component trait factoring,
`SaveImages` retained-artifact policy, `RelateObjects` endpoint SSOT,
`CorrectIlluminationApply` provenance ownership, and generic compiler
validation hooks.

## Design Goal

Make AutoRegisterMeta-backed module class declarations the single CellProfiler
module semantic authority for catalog generation, generator lowering, compiler
validation, and runtime policy selection.

The important move is not to add another parallel class layer. It is to make the
class that represents the module pay rent and make lower-level policy families
execute declared semantics:

- the `CellProfilerModule` class owns module-level semantics and declares the
  binding/function/contract/runtime policies for modules that need non-generic
  behavior;
- `AbsorbedFunctionMetadata`, `validated_contracts()`, and legacy catalog
  exports are derived projections of those class declarations, not independent
  registries.
- `_ModuleSettingsBindingStrategy` can execute settings-to-kwargs mechanics
  during migration, but module declarations own the binding selection,
  setting aliases, ignored settings, and postprocess semantics.
- Artifact contracts and compiler-visible validation hooks belong on
  `CellProfilerModule` declarations or inherited declaration mixins.
  `ModuleContractBuilder` is a legacy migration target, not a semantic owner to
  preserve as a parallel registry.
- Function resolution should be automatic from module declarations:
  `function_name`, `function_variants`, aliases, and optional declaration
  override hooks select the backend callable. `_ModuleFunctionResolutionStrategy`
  can remain only as helper/executor code while callers migrate.
- Module-revision runtime kwargs belong on module declarations or inherited
  revision mixins. `ModuleRuntimeSemanticsBinding` can remain only as generic
  mechanics while callers migrate.
- `module_processing_components.py` owns generic source-axis lowering algebra and
  default execution-scope machinery. Module-named processing semantics are owned
  by the `CellProfilerModule` class.
- runtime policy ABCs such as `CellProfilerSpecialInputPolicy`,
  `CellProfilerObjectInputPolicy`, and
  `CellProfilerInvocationExecutionModePolicy` define executable contracts and
  shared mechanics. Module-specific facts should be selected from the
  `CellProfilerModule` declaration, not by a second module-name lookup path.

The generator and runtime should consume already-selected policy objects or
plans. They should not create a new facade that merely repeats registry lookup.

## Existing Nominal Declaration Families

### Module Class Contract

Execution-scope and binding semantics should be declared on the class that
represents the CellProfiler module. All CellProfiler module classes should
inherit the same ABC root. That ABC is the abstraction: it is both the contract
and the AutoRegisterMeta registry root. Do not add a second declaration object
beside it.

```python
class CellProfilerModule(ABC, metaclass=AutoRegisterMeta):
    __registry_key__ = "module_name"
    __skip_if_no_key__ = True

    module_name: ClassVar[str]

    function_name: ClassVar[str]
    aliases: ClassVar[tuple[str, ...]] = ()
    enforced_variable_components: ClassVar[tuple[VariableComponents, ...] | None] = None
    setting_bindings: ClassVar[tuple[SettingToKeywordBinding, ...]] = ()
    ignored_settings: ClassVar[tuple[str | SettingNameFamily, ...]] = ()

    @classmethod
    def postprocess_bound_settings(
        cls,
        module: ModuleBlock,
        bound: BoundModuleSettings,
    ) -> BoundModuleSettings:
        return bound

    @classmethod
    def processing_components(
        cls,
        request: ModuleProcessingComponentRequest,
    ) -> ModuleProcessingComponents: ...

    @classmethod
    def module_requires_pairwise_object_domain_scope(
        cls,
        contract: ModuleArtifactContracts,
    ) -> bool: ...
```

The concrete modules inherit from this root:

```python
class TrackObjects(CellProfilerModule):
    module_name = "TrackObjects"
    function_name = "track_objects"
    enforced_variable_components = (VariableComponents.TIMEPOINT,)
```

If a module enforces a specific `variable_components` value, that fact is
declared on the module class through the ABC contract. It must not be repeated
in `pipeline_generator.py`, `contracts.json`, `AbsorbedModuleMetadata`,
compiler validation, runtime adapter tables, or generated metadata mirrors.
Those callers query the registered `CellProfilerModule` class and derive the
generated `FunctionStep` declaration from that one owner.

The generator should not contain repeated local algorithms for individual
CellProfiler modules, and the catalog must not be a second registry that repeats
class facts. The compiler-facing validation hook should follow the same rule:
generic compiler code supplies a step/configuration context, and the module
class or its selected policy ABC returns a typed validation result or raises a
precise configuration error.

### Module-Local Semantic Ownership

All logic for a concrete CellProfiler module belongs with that module's existing
policy/strategy declarations. `RelateObjects` is the model case: parent/child
relationship endpoints, relationship measurement rows, parent/child count
features, special inputs, object-row completion, and export/runtime projections
must be owned by `RelateObjects` policy leaves or shared parents those leaves
inherit from. If the adapter, exporter, generator, or runtime needs one of those
facts, it queries the `RelateObjects` policy. It must not duplicate the
relationship semantics locally.

### Infrastructure Policy Contract

Skipped infrastructure modules also need policy declarations. Use the existing
`CellProfilerInfrastructureImportNote` family first and extend it only if the
contract cannot express retained artifacts:

```python
class CellProfilerInfrastructureImportNote(ABC):
    def retained_artifacts(
        self,
        module: ModuleBlock,
        contracts: Mapping[int, ModuleArtifactContracts],
    ) -> frozenset[ArtifactSpecKey]: ...
```

This replaces generator-local helpers like `_save_images_required_artifacts`.
For `SaveImages`, the retained artifact policy should parse the source-image
setting and return the required `ArtifactSpecKey`. For `ExportToDatabase`, the
policy should state that a post-execution export is required, while the CPA
export implementation handles the project profile.

### Setting-Derived Scope

Some behavior is not static. `CorrectIlluminationCalculate` depends on
`calculation_scope`. That should be represented as a setting-derived policy:

```python
class ModuleSettingScopePolicy(ABC):
    def processing_components(
        self,
        request: ModuleProcessingComponentRequest,
        default_components: ModuleProcessingComponents,
    ) -> ModuleProcessingComponents: ...
```

The policy can stay module-specific, but it should live on the module's existing
processing/settings policy leaf or a parent/mixin it inherits from, not in the
generator.

## Adjacent High-Risk Follow-Up Files

A lightweight scan of `openhcs/interop/cellprofiler` and `openhcs/runtime`
found several files with the same risk profile as `pipeline_generator.py`: large
semantic hubs that mix dispatch, policy, external compatibility rules, and
runtime wiring. These should be considered after the generator boundary is in
place.

The ranking below is based on size, number of strategy/policy classes, direct
module/viewer-specific behavior, and proximity to bugs already seen in source
binding, streaming axes, and CellProfiler runtime output semantics.

### Priority 1: CellProfiler Runtime Module Execution

```text
openhcs/interop/cellprofiler/runtime/module_execution.py
```

Observed risk:

- approximately 4,300 lines;
- dozens of runtime policies in one file;
- owns runtime callable binding, image execution strategy selection, object
  input policies, special input policies, measurement materialization entry
  points, relationship handling, and dual-scope measurement policy;
- contains many module-named policy leaves, such as `MaskImage`,
  `RelateObjects`, `Watershed`, `StraightenWorms`, `ClassifyObjects`, and
  measurement-specific policies.

Why this is related:

The generator should select existing module policies for compile-time lowering.
The runtime needs the same architecture for execution-time behavior. Existing
policy families should be able to answer both:

- how this module lowers into an OpenHCS `FunctionStep`;
- how this module binds special/runtime inputs when the step executes.

Likely refactor:

- split runtime policies into existing-ABC-owned families:
  - image execution policy;
  - object input binding policy;
  - special input binding policy;
  - measurement-output policy;
  - dual-scope measurement policy;
- keep a small `CellProfilerRuntimeCallable` orchestration layer that asks those
  selected policies instead of carrying module-specific logic locally.

Acceptance:

- `module_execution.py` becomes an execution coordinator, not a policy catalog;
- module-named runtime behavior is discoverable through existing ABC registries;
- generator and runtime cannot disagree about a module's special inputs,
  measurement scope, or object-domain semantics.

### Priority 2: CellProfiler Settings Binding

```text
openhcs/interop/cellprofiler/module_settings_binding.py
```

Observed risk:

- approximately 3,300 lines;
- more than 100 classes;
- owns generic setting binding plus many module-specific binding strategies;
- already imports `ModuleRuntimeSemanticsBinding`, which means runtime-family
  decisions can leak into settings translation.

Why this is related:

Settings binding is module policy, not code generation. The generator should
ask the existing `_ModuleSettingsBindingStrategy` family for already-bound
kwargs and invocation options. It should not duplicate binder semantics or know
which settings within a module imply runtime behavior.

Likely refactor:

- keep `_ModuleSettingsBindingStrategy` as the owner and strengthen its ABC
  contract;
- split large module-specific binders into focused setting-family modules where
  they are not already split;
- make setting coverage records an output of the module generation plan, not a
  generator-local side channel.

Acceptance:

- adding a new module-specific setting binding does not require touching
  `pipeline_generator.py`;
- the existing settings-binding registry can list modules with custom settings
  binding;
- setting-derived execution behavior is represented as typed policy, not
  incidental kwargs.

### Priority 3: Symbol Table And Artifact Contracts

```text
openhcs/interop/cellprofiler/symbol_table.py
```

Observed risk:

- approximately 2,800 lines;
- owns symbol identity, source bindings, artifact contracts, inferred contract
  patterns, literal code rendering, and many module-named contract builders.

Why this is related:

Artifact contracts are one of the core module-policy products. The symbol table
should remain the workspace-name authority, and `ModuleContractBuilder` should
remain the module-specific contract authority. Other code should query that
existing family instead of building a second contract-rule catalog.

Likely refactor:

- keep `CellProfilerSymbolTable` focused on symbol storage and lookup;
- split generated-code literal rendering out of the symbol table if it remains
  only for generated source emission;
- make inferred contract patterns a `ModuleContractBuilder` feature with explicit
  confidence/diagnostic output.

Acceptance:

- symbol table compiles contracts through `ModuleContractBuilder`;
- symbol storage, contract inference, and generated-code literal rendering are
  separate owners;
- contract builders remain nominal and fail loudly for unsupported modules.

### Priority 4: Source Candidate And Runtime Source Binding

```text
openhcs/interop/cellprofiler/runtime/source_candidates.py
openhcs/interop/cellprofiler/runtime/source_binding_runtime.py
openhcs/interop/cellprofiler/runtime/source_identity.py
```

Observed risk:

- `source_candidates.py` is approximately 1,900 lines;
- `source_binding_runtime.py` is approximately 1,360 lines;
- these files decide how source metadata, aliases, planes, path identity,
  current-step payloads, and pipeline-start payloads become runtime inputs.

Why this is related:

This is the runtime counterpart to source-schema lowering. The architecture only
works if source identity is centralized. Any local interpretation here can
recreate the same bugs that showed up in streaming axes and CPA source-row
projection.

Likely refactor:

- define a core-owned source candidate/query API that represents:
  - source image set identity;
  - alias-to-plane resolution;
  - structured source refs;
  - current-step versus pipeline-start source origin;
- make CellProfiler runtime source binding a profile over that core API;
- remove local fallback path identity logic where a typed source projection can
  answer the question.

Acceptance:

- source binding runtime does not infer channel/site/well identity from paths
  when structured metadata exists;
- source candidate matching is testable without executing a CellProfiler module;
- CPA source-row reconstruction and runtime source binding share the same core
  source projection authorities.

### Priority 5: Measurement Materialization And Object Row Policies

```text
openhcs/interop/cellprofiler/runtime/measurement_materialization.py
openhcs/interop/cellprofiler/runtime/object_measurement_row_policies.py
openhcs/interop/cellprofiler/runtime/measurement_rows.py
openhcs/interop/cellprofiler/runtime/relationship_measurement_rows.py
```

Observed risk:

- these files translate CellProfiler row shapes into core
  `MeasurementTable`, object row ownership, image numbers, and relationships;
- they sit directly on the boundary needed by CPA export and runtime parity.

Why this is related:

The generator declaration refactor makes compile-time module semantics
queryable. Measurement materialization needs the same treatment for row
semantics: scope, ownership, object id fields, source image name, relationship
endpoints, and image-number projection should be queryable declarations or core
row-projection policies.

Likely refactor:

- move row ownership and image-number behavior into core measurement row
  projection policies where possible;
- keep CellProfiler-specific dialect names at the interop edge;
- make relationship row construction produce typed relationship graphs rather
  than database/export-specific rows.

Acceptance:

- runtime measurement tables and CPA export tables consume the same row
  projection facts;
- object-label measurement, relationship, and per-image rows cannot diverge in
  their interpretation of image number or object identity;
- CellProfiler-specific feature-name parsing is isolated from core row
  projection.

### Priority 6: Napari/Fiji Viewer Servers

```text
openhcs/runtime/napari_viewer_server.py
openhcs/runtime/fiji_viewer_server.py
openhcs/runtime/napari_streaming_handlers.py
openhcs/runtime/viewer_component_system.py
openhcs/runtime/viewer_protocol.py
```

Observed risk:

- `fiji_viewer_server.py` is approximately 2,750 lines;
- `napari_viewer_server.py` is approximately 2,500 lines;
- both include transport/server code near viewer-specific payload handling;
- `napari_streaming_handlers.py` owns layer keys, batching, axis projection,
  label rasterization, and presentation behavior;
- `viewer_component_system.py` is the shared semantic owner but is also large
  enough that it can become a catch-all.

Why this is related:

The viewer bugs came from local interpretation of component axes and payload
identity. This is the same class of issue as generator-owned module semantics:
viewers should query a shared declaration/profile for component layout,
payload-type handling, and presentation behavior.

Likely refactor:

- introduce a viewer route/profile query layer:
  - shared route identity;
  - component axis projection;
  - data-type handler registry;
  - payload presentation profile;
  - transport-specific writer;
- keep Napari/Fiji differences as profile declarations, not duplicated control
  flow;
- split server lifecycle from payload rendering.

Acceptance:

- adding or changing a streaming payload type registers a handler/profile once;
- Napari and Fiji consume the same component-axis and route-identity decisions;
- viewer server files become transport/lifecycle coordinators.

### Priority 7: ZMQ Execution Server

```text
openhcs/runtime/zmq_execution_server.py
```

Observed risk:

- combines request payload resolution, config-code policy, orchestrator setup,
  compile-only behavior, execution behavior, progress publication, and result
  shaping;
- not as module-semantic-heavy as the CellProfiler files, but it is a runtime
  boundary hub.

Likely refactor:

- split transport request parsing from execution planning;
- make compile/execute modes explicit request strategies;
- keep ZMQ serialization separate from orchestrator execution policy.

Acceptance:

- direct execution, ZMQ execution, and future agent execution can share the same
  execution request model;
- ZMQ server owns transport and lifecycle, not execution semantics.

## Suggested Follow-Up Order

1. Finish the generator selected-policy planning boundary.
2. Make runtime module execution consume selected existing policies through one
   thin generic path.
3. Move settings binding, function resolution, and artifact-contract selection
   onto `CellProfilerModule` declarations; keep binder/resolver/compiler code as
   generic execution mechanics only.
4. Refactor source candidate/source binding runtime around core source
   projection authorities.
5. Refactor measurement/object/relationship row projection for CPA and runtime
   parity.
6. Apply the same query/profile pattern to Napari/Fiji viewer routes and payload
   handling.
7. Split ZMQ execution server after semantic boundaries are stable.

This order keeps the highest semantic-risk CellProfiler boundaries ahead of
transport cleanup. It also lets the CPA export plan reuse the source and
measurement projection work instead of building a parallel exporter-specific
model.

## Architectural Judgements To Encode Before Codemodding

These decisions are not codemod decisions. They are the semantic boundary the
codemod is allowed to enforce.

| Judgement | Decision | Why |
| --- | --- | --- |
| Module catalog authority | AutoRegisterMeta-backed module class declarations are the module-level authority. The absorbed catalog, JSON exports, and DTO/catalog views are generated projections. Existing ABC families execute specific axes such as settings binding, artifact contracts, function resolution, and runtime policies. Do not add facades that only delegate to them. | The repo already has nominal families and metaclass registration; the problem is weak module-level ownership and duplicated lookup, not absence of wrappers. |
| Generator ownership | `pipeline_generator.py` owns parsing orchestration, module partitioning, dead-artifact pruning, generation-plan construction, and source emission. It does not own module-specific CellProfiler behavior. | The generator should be stable when a CellProfiler module gains new semantics; only declarations/policies should change. |
| Module-local ownership | A concrete module's semantics belong with that module's policy leaves. For example, `RelateObjects` relationship endpoints, parent/child count rows, and projection/export facts belong to `RelateObjects` policies; callers query them. | This prevents adapter, exporter, generator, and runtime code from carrying duplicate versions of one module's rules. |
| JSON catalog status | `contracts.json` is a compatibility artifact until removed. Do not add new semantic fields to it. | Adding nested generation or binding metadata to JSON recreates the same parallel registry the declaration refactor is meant to remove. |
| Enforced variable components | If a module forces a specific `variable_components` value, that fact lives on the `CellProfilerModule` class through `enforced_variable_components` or an equivalent ABC hook. | This prevents `TrackObjects`-style axis rules from being copied into generator branches, catalog JSON, compiler checks, or runtime adapter tables. |
| Compiler validation | Compiler and validation code should validate CellProfiler-backed steps by consulting existing policy hooks. It must not recover module semantics through concrete module-name branches. | This keeps step validity a generic property of `FunctionStep + selected CellProfiler policies`, not a parallel rule system in compiler/runtime infrastructure. |
| Runtime ownership | `runtime/module_execution.py` owns runtime request construction, execution sequencing, adapter interaction, and output recording mechanics. It should consume selected policies rather than choosing module policies repeatedly. | Runtime bugs come from compile/runtime semantic drift. Selecting policy once prevents separate paths from disagreeing. |
| Generic lowering machinery | Generic source-axis and runtime-artifact scope algebra can stay near the generator until it has a clearer shared owner. Module-named behavior must live on existing module policies. | Moving generic algebra too early creates churn; leaving module behavior in the generator preserves the leak. |
| Runtime request records | Request/data classes such as `SpecialInputBindingRequest`, `ObjectInputBindingRequest`, `CellProfilerModuleRuntimePlan`, and `CellProfilerModuleExecutor` are runtime mechanics unless they contain module-specific selection. | These objects encode execution context, not CellProfiler module declarations. Moving them blindly would make policy modules depend on runtime internals. |
| Static vs setting-derived semantics | Setting-derived behavior should be represented by typed dynamic policy objects, not flattened into static declaration constants. | Modules like `CorrectIlluminationCalculate` change behavior based on settings; a static record would hide real runtime/generator conditions. |
| Infrastructure modules | Skipped infrastructure modules such as `SaveImages` and later `ExportToDatabase` should declare artifact/export requirements. The generator should ask for requirements. | Pruning and export compatibility need to see infrastructure consumers without hardcoded generator helpers. |
| Generated pipeline boundary | Generated Python should not receive policy plumbing unless integration tests prove it is required. Prefer selecting policies from the runtime contract module name inside the executor. | Generated pipelines should stay small and stable; policy selection is product runtime infrastructure. |
| Advisor role | Advisor output is an acceptance gate on touched backend files, not the source of architectural truth. | The advisor can detect under-abstraction symptoms and local role-case logic; humans still choose the boundary and encode it as invariants. |

Codemod work is valid only after these judgements are encoded as tests or
explicit invariants. If a transform has to infer one of these judgements from
domain meaning, it should report an ambiguous candidate and stop.

Batch order:

1. Mechanical declarative settings only: move literal `setting_bindings` from
   `*ModuleSettingsBindingStrategy` leaves onto the matching
   `CellProfilerModule` subclass, then remove the duplicate leaf/constant.
2. Module-local overrides: migrate `_bind` overrides only when the override can
   become a direct `CellProfilerModule.postprocess_bound_settings(...)` or a
   declared module method queried by generic binding execution.
3. Complex binders: leave custom workspace/threshold/object-measurement binders
   in existing parent classes until a shared parent removes real duplication.
   The module class should still be the only place that selects the module's
   binding semantics.

## Risks

- A selected-policy plan can become another god object if it owns behavior
  instead of carrying already-selected policies.
- Moving strategies too early can make diffs noisy. First make existing ABC
  contracts pay rent, then migrate one behavior family at a time.
- Some module behavior is setting-derived, not static. Do not force it into
  static records; use typed setting-derived policy objects.
- Some semantics belong to backend callable metadata, but not all. Pipeline
  lowering behavior, source-axis behavior, and infrastructure export behavior
  should stay in CellProfiler interop policy families rather than being pushed
  into absorbed backend functions.
- Codemods can make an architectural leak look consistent. Every codemod stage
  must have an invariant and a test before applying broad rewrites.

## End State

`pipeline_generator.py` should read as:

1. load absorbed registry metadata;
2. partition executable and infrastructure modules;
3. compile source schema and symbol contracts through existing policy owners;
4. build module generation plans from selected existing policies;
5. prune dead artifacts using infrastructure-policy artifact requirements;
6. render source code from already-lowered plans.

The generator should not be the first place an engineer edits when a
CellProfiler module has new semantic behavior. The first place should be the
module's existing policy/strategy leaves or a shared parent those leaves inherit
from.
